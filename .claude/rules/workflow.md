# Rules: Spec-Driven Development Workflow

目的：仕様（Spec）で意図を明確にし、テストで正しさを検証し、最小差分で安全に進める。

Spec-Driven = 仕様が主軸。TDD はAIが生成したコードの検証装置として機能する。

## 0) 原則
- SIMPLE = GOOD, COMPLEX = BAD
- 提案（設計/選択肢）と実装（コード変更）は分ける
- 迷うポイントを先に潰す（後工程での手戻りを最小化）
- Verify を先に用意する（テスト/コマンド/手順。無いなら先に提案/作る）

## 1) 標準フロー（Explore → Plan → Spec → Test → 実装）

### 1.1 Explore（探索）
- 目的の確認に必要な範囲だけ読む（最小の関連ファイル / 既存仕様 / ログ）
- 不明点は仮説として扱い、断定しない

### 1.2 Plan（計画）
- 小変更（タイポ、コメント、ログ1行、明確なlint修正）以外は Plan を書いてから着手
- Plan には以下を含める：
  - 変更点の要約（1〜5行）
  - 影響範囲
  - verify 方法（テスト/コマンド/手順）
  - リスク分類（High/Low）

### 1.3 Spec → Test → 実装
1. **要件確認**: 要件を1〜3行で言い換える（ズレやすい前提だけ潰す）
2. **Mini Spec 作成**: 仕様を構造化して書く（→ セクション2参照）
3. **Acceptance Criteria 作成**: 検証可能な受け入れ条件を書く（→ セクション3参照）
4. **実装方針決定**: 最小案 + 代替があるなら1つだけ提示
5. **テスト作成**: Acceptance Criteria に基づきテストを先に書く（→ セクション4参照）
6. **実装**: 最小差分でコーディング（影響が広ければ分割）
7. **検証**: 型/Lint/単体テスト/主要導線
8. **報告**: 何を変えた / なぜ / どう確認したか（→ セクション10参照）

## 2) Mini Spec（必須）

実装前に以下を構造化して書く（長くしない。1画面を目安）。
AI が正確に解釈できるよう、曖昧語を排除し、入出力を具体的に記述する。

```
Goal: [1行で目的を記述]
Non-goals: [やらないこと / 今回スコープ外]

Behavior:
  Input: [入力データ・トリガー・ユーザー操作]
  Process: [処理内容（状態遷移があれば明記）]
  Output: [出力データ・表示・レスポンス]
  Example:
    - [具体的な入出力例を1〜2個]

Edge cases:
  - [条件]: [期待される挙動（エラー表示/ログ/リトライ等）]
  - [条件]: [期待される挙動]

Contract impact: [なし / あり → 以下を記述]
  - 影響対象: [API互換 / データ構造 / 認証・権限 / 課金 / 主要導線]
  - リスク: High（明示OK必須）

Rollback: [戻し方を1行で記述]
```

記入例:
```
Goal: 期限切れトークンでのAPIアクセス時に401を返す
Non-goals: トークンの自動更新（今回スコープ外）

Behavior:
  Input: Authorization ヘッダーに期限切れJWTを含むGETリクエスト
  Process: トークンの有効期限を検証 → 期限切れなら認証エラー
  Output: HTTP 401 + {"error": "token_expired", "message": "トークンが期限切れです"}
  Example:
    - 期限切れトークンでGET /api/profile → 401 token_expired
    - トークンなしでGET /api/profile → 401 token_missing

Edge cases:
  - 不正な形式のトークン: 401 + invalid_token エラーを返す
  - 改ざんされたトークン: 401 + invalid_token エラーを返す（署名検証失敗）

Contract impact: なし（既存の401レスポンス形式に準拠）

Rollback: 認証ミドルウェアの該当コミットをrevert
```

## 3) Acceptance Criteria（必須）

- 3〜7個の箇条書き
- 曖昧語を使わない（「いい感じに」ではなく「〜ができる/〜になる」）
- 1項目＝1検証観点（テストケースに直結する粒度）
- Given/When/Then 形式を推奨（テスト生成しやすくするため）
- 各項目に verify 方法を紐づける（テスト名 / コマンド / 手動手順）

記述例:
```
- [ ] Given: ユーザーが未ログイン状態
      When: /api/profile にGETリクエスト
      Then: 401エラーが返る
      Verify: test_unauthorized_profile_access

- [ ] Given: 有効なトークンを持つユーザー
      When: /api/profile にGETリクエスト
      Then: ユーザー情報のJSONが返る（name, email を含む）
      Verify: test_authorized_profile_access
```

## 4) テストによる検証（AI出力の検証装置）

AI が生成したコードが仕様通りか確認するために、テストを検証装置として使う。

### 4.1 テストの役割
- **仕様の固定**: Acceptance Criteria をテストコードに変換し、期待挙動を機械的に検証可能にする
- **回帰防止**: 既存の挙動が壊れていないことを自動で検出する
- **仕様の明文化**: テスト自体が「この関数/機能は何を保証するか」のドキュメントになる

### 4.2 機能追加・仕様変更
- 期待挙動をテストで先に書く（Red → Green → Refactor。UIのみの変更や設定値の変更など、テストで表現しにくい場合は手動検証手順で代替可）
- テスト名は「何が保証されるか」を文で書く
  - 良い例: `test_expired_token_returns_401`
  - 悪い例: `test_token_1`

### 4.3 バグ修正
- 再現 → 原因切り分け → 修正方針 → 修正 → 再発防止（回帰テスト）
- 先に「落ちるテスト（回帰テスト）」を追加してから修正する

### 4.4 テスト対象
- Unit テストを優先する: 外部依存なしのロジック（ユーティリティ、モデル、バリデーション、変換、ビジネスロジック）

### 4.5 外部依存の扱い
- 外部I/Oは interface 化し、Fake/Stub で unit を安定させる
- Integration は emulator / ローカルで再現可能にする

## 5) リスク分類（明示OKが必要）
### 5.1 High Risk（事前に明示的OKが必要）
- 互換性破壊（API互換・データ構造・認証/権限・課金・主要導線）

進め方：
1. 原因/背景を短く説明
2. 修正案（最小案）とリスクを提示
3. Rollback を明記
4. 明示的な承認を得てから着手

### 5.2 Low/Medium（OKなしで進めてよい）
- ローカルなバグ修正、UI崩れ、タイポ、ログ追加、軽微リファクタ
- スコープが明確にローリスクなら承認なしで進めてよい

ただし報告に必ず入れる：
- 影響範囲
- 確認方法（再現手順/動作確認）
- 戻し方（ロールバック/変更点の要約）

## 6) Definition of Ready（着手条件）
- Mini Spec がある（必須）
- Acceptance Criteria がある（必須）
- リスク分類（High/Low）が明確（必須）
- verify 手段（テスト/コマンド/手順）が1つ以上ある（必須）
- 影響範囲とRollbackが1行で書ける（推奨）

## 7) Definition of Done（完了条件）
- 依頼範囲を満たす（必須）
- Acceptance Criteria を満たす（テスト or 検証手順がある）（必須）
- 既存機能を壊していない（主要導線の確認）（必須）
- 失敗時の挙動（表示 or ログ）が最低限ある（必須）
- バグ修正は回帰テストが追加されている（必須）
- behavior/contract が変わるなら docs 更新（必須）

## 8) 単体テスト（iOS）
- 関数を追加・修正したら、対応する単体テストを追加する
- テスト対象: 外部依存のないユーティリティ、モデル、ビジネスロジック

## 9) 単体テスト（Server）
- 関数を追加・修正したら、対応する単体テストを追加する
- テスト対象: 外部依存のないユーティリティ、バリデーション、ビジネスロジック

## 10) 報告フォーマット（必須）
- 変更点: 何を変えたか（箇条書き）
- 理由: なぜそうしたか（Mini SpecのGoalに紐づける）
- 確認: どう確認したか（コマンド/手順/導線）
- リスク: 影響範囲 / Rollback
- テスト: 追加/更新したテスト（該当ファイル名とテスト内容）
